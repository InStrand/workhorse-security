# whs command-line audit and doctor design (bead whs-m6y.3.18, phase 1)

Reviewer: an agent that did not write `whs`. Date: 11 November 2026.
Subject: the code as first written, before the architecture pass of 12 November, read and run from a snapshot. Nothing in the live repository was read, run or edited. Trials used throwaway repositories under `a scratch folder/`.
Paths below are shortened: `<pack>` is the pack root, `~` is the home directory.

Method: the scoring rubric of `agent-ergonomics-and-intuitiveness-maximization-for-cli-tools` (eleven dimensions, anchors at 0, 250, 500, 750 and 1000) applied to the whole CLI, and the kernel of `world-class-doctor-mode-for-cli-tools` applied to a doctor for a tool whose only writes are in a cache directory. Section 4 lists what was left out of each skill and why.

Size of the tool by the skill's own count: 6 commands, 11 options, 5 environment variables, 3 exit codes. That is about 25 surfaces, the skill's smallest tier (30 or fewer, one worker).

## 3. The doctor design

### Commands

```
whs doctor                 check this machine and this copy of the pack
whs doctor <repo>          the same, plus the repository's config at HEAD (or --ref <ref>)
whs doctor --json          one JSON document on stdout
whs doctor --fix           apply the repairs doctor can make itself, then check again
```

No other subcommands or options. A plain `whs doctor` is the dry run: every finding states what `--fix` would do, or the command or edit that fixes it.

Doctor makes no network call. Its main cost is asking the three scanners for their versions, which took 1.3 seconds here, so a run should take under two seconds.

### Checks

Each check belongs to one group. The group decides whether a problem can fail the run.

- gate: needed to run `gate` and `scan`. A problem is `fail`.
- audit: needed for `audit prepare`. A problem is `warn` at most, because `audit prepare` fetches the pinned process itself and every other source is optional.
- push: needed to push to the pack. Applies only when the pack root is a git work tree and `CI` is not set; otherwise `skip`. A problem is `fail`.
- target: only with `doctor <repo>`.

### JSON shape

```json
{
  "schema": 1,
  "command": "doctor",
  "whs": { "version": "0.1.0", "commit": "<sha>", "pack": "/abs/pack" },
  "outcome": "findings",
  "summary": { "pass": 17, "warn": 2, "fail": 1, "skip": 2 },
  "context": {
    "platform": "darwin-arm64",
    "cache": "/abs/cache/workhorse-security",
    "coverage_mode": "full",
    "target": { "path": "/abs/repo", "commit": "5b7dd986...", "fragments": ["postgres-supabase"] }
  },
  "checks": [
    {
      "id": "tool.semgrep",
      "group": "gate",
      "status": "fail",
      "summary": "semgrep 1.185.0 does not run or reports another version: venv/bin/semgrep exited 127",
      "detail": { "home": "/abs/cache/workhorse-security/tools/semgrep-1.185.0", "stamp": "match", "binary": "present", "reported": null },
      "fix": {
        "kind": "doctor-fix",
        "command": "node /abs/pack/bin/whs.mjs doctor --fix",
        "moves": { "from": ".../tools/semgrep-1.185.0", "to": ".../tools/.quarantine/semgrep-1.185.0.1" }
      }
    }
  ],
  "actions": [],
  "next": ["node /abs/pack/bin/whs.mjs doctor --fix", "node /abs/pack/bin/whs.mjs install"]
}
```

Rules for the shape:

- `outcome` is `pass`, `findings` or `error`, the same three words `summary.json` uses, and it always agrees with the exit code.
- `status` is `pass`, `warn`, `fail` or `skip`. `fix` is `null` or has `kind` `command` (run it; safe to repeat), `doctor-fix` (`--fix` does it) or `manual` (with `text`).
- `context.target` is `null` without a repository. `actions` is filled only by `--fix`: one `{ "op": "move", "from", "to" }` per move.
- Check ids are never renamed. A new check or a new key is an addition. `schema` changes only when a key is removed or changes meaning. A test pins the key set.
- No timestamps and no durations, so two runs on the same state print the same bytes.
- Checks are listed in a fixed order: gate, audit, push, target.

Text output is one line per check (`ok`, `warn`, `FAIL`, `skip`, the id, the summary), the fix on the next line for anything that is not `ok`, then a count line and `next:`.

### Exit codes

| Code | Doctor | Same meaning elsewhere in whs |
|---|---|---|
| 0 | No check failed. Warnings and skips are allowed. | pass |
| 1 | At least one check failed. With `--fix`, at least one still fails after the repairs (for example a tool that now needs `whs install`). | findings |
| 2 | Doctor could not do its job: a usage error, a repository path or ref that does not exist, or a repair that itself failed. | a check or the command failed |

An invalid registry is a failed check (exit 1), and the other checks still run. Today an invalid registry stops every command before it starts, so doctor is dispatched before the registry is loaded.

### How the skill's chokepoint and backup rules map onto this tool

The skill requires that every write under `--fix` goes through one function that backs the file up, records hashes, and can be undone. `whs doctor` has one kind of repair, so the mapping is short.

- One function, `moveAside(path)`, is the only code in `lib/doctor.mjs` that changes anything on disk. It renames a directory into a `.quarantine/` directory beside it: `<tools>/semgrep-1.185.0` becomes `<tools>/.quarantine/semgrep-1.185.0.1`. The number counts up, the way `run-N` does in `audit prepare`.
- It refuses any path that does not resolve to somewhere inside the tools directory or the sources directory, and returns a failed repair (exit 2) with the reason.
- It never deletes and never overwrites. A test searches `lib/doctor.mjs` for `rmSync`, `unlinkSync`, `rmdirSync` and `writeFileSync` and fails if one appears.
- The backup rule is met by the move itself: the directory that was there is still there, byte for byte, under `.quarantine/`. The undo is the reverse `mv`, which doctor prints. There is no undo command, no run directory, no action log and no hashes, because nothing is rewritten. Section 4 gives the reasoning.
- Run twice equals run once: the second `--fix` finds nothing to move and reports no actions.
- Two `--fix` runs at once: the rename happens once. The other run finds the directory gone, reports that, and carries on. No lock file.

What `--fix` repairs in the first version:

1. A tool directory whose binary does not run or reports another version (the usual cause is a virtual environment whose Python was upgraded away). Moved aside. The next step is `whs install`.
2. A pinned source directory that is not a usable git checkout. Moved aside. The next step is `whs install --sources` or `whs audit prepare`.

Everything else is a command to run or an edit for a person or agent to make. `--fix` never touches the term list, git configuration, the registries or the target repository. If item 8 in section 2 is built, `install` handles case 1 by itself and `--fix` is left with case 2 only; section 5 asks about this.

### Tests for the doctor (`test/doctor.test.mjs`)

Each test builds its state in a temporary directory through `WHS_TOOLS_DIR`, `XDG_CONFIG_HOME`, `WHS_CONFIDENTIAL_TERMS`, `WHS_SKILLS_DIRS` and a fixture pack root, the way the existing loaders already accept `packRoot`. A hand-made tool directory (a stamp file and a script that prints a version) stands in for a real scanner, so the tests need no network.

1. A healthy fixture exits 0; the JSON key set equals the pinned list.
2. A missing tool directory fails `tool.<name>`, and `fix.command` ends with `install`. Exit 1.
3. A stamp that differs from the registry fails with `installed for a different pin`.
4. A binary that exits non-zero fails with `kind: doctor-fix`. `--fix` moves the directory to `.quarantine/<name>-<version>.1` with its contents unchanged. A second `--fix` reports no actions.
5. A plain `doctor` and `doctor <repo>` change nothing: the list of every path, size and modification time under the fixture is the same before and after.
6. `lib/doctor.mjs` contains no deleting or writing call, and `moveAside` refuses a path outside the cache.
7. Target: no config warns; an invalid config fails; an expired exception warns with its index and date; a data path that matches no file warns with the pattern; an uncommitted edit to the config warns.
8. Push: with `core.hooksPath` unset in a fixture clone, `hooks.path` fails and names `dev-setup.sh`; with `CI=true` it is `skip`. A missing term list fails; a list with a planted term passes and the term appears nowhere in stdout or stderr.
9. An invalid registry in a fixture pack fails `registry.checks` with exit 1, and the other checks are still reported.
10. `--json` prints one JSON document, and two runs print identical bytes.

Size of the doctor work: M. About 250 lines in `lib/doctor.mjs`, 20 lines of exports and wiring, 180 lines of tests. Roughly a third of phase 2.

## 5. Open questions for the owner

1. Should `whs doctor --fix` stop at local repairs, or also run the install?
   Recommendation: local repairs only. `--fix` moves a broken tool or source directory aside and then names `whs install` as the next command. It stays offline, quick and testable without a network, and an agent in a sandbox gets the same result as one with network access. If you would rather have one command, the smaller design is to make `install` repair a broken virtual environment itself (item 8) and keep doctor read-only apart from pinned sources.

2. `whs gate --base <ref>` where the ref is not zero and does not resolve (a shallow clone, or the old tip after a force push): keep judging it as a first push, or refuse with exit 2?
   Today it is silently judged as a first push: the whole history is scanned, every finding counts, and the exceptions are read from the head revision, so in that one case a change can carry its own exception. Refusing would be stricter, but GitHub's `before` commit after a force push is often absent from a fresh clone, so refusing would turn every force push to the default branch into an error. Recommendation: keep the behaviour in phase 2 and make it loud (the text says the base did not resolve and why that matters, and `summary.json` records `base_requested` and `base_resolved: false`). Decide separately whether an unresolved base should also ignore the head's exceptions; that is a change to the standard and needs a planted negative in `test/gate.test.mjs`.

3. Does `whs init <repo>` belong in this bead?
   Recommendation: its own bead, after doctor. It writes a workflow into another repository pinned to the pack's commit, which only works across organisations once the pack is public (decision D9), and its natural check is `doctor <repo>` (`target.workflow` and `target.config`), which has to exist first. If you want it in this bead, it is item 7, size M, and I would build it last.
